\section{Experimental Evaluation}
In this section, we evaluate our lightweight GCN approach for build failure prediction. Rather than comparing against dynamic coverage-heavy SOTAs that are unscalable in our target LRTS environment, we focus on establishing an empirical baseline using available static and metadata features.

\subsection{Evaluation Plan}
Our evaluation is guided by the following Research Questions (RQs):
\begin{itemize}
    \item \textbf{RQ1 (Predictive Performance):} How effectively can a lightweight GCN encoder, combined with CI metadata, predict failing builds using only static call graphs?
    \item \textbf{RQ2 (Decision Thresholds):} How does tuning the decision threshold affect the trade-off between Precision and Recall in a highly imbalanced LRTS dataset?
    \item \textbf{RQ3 (Root Cause Analysis):} What are the fundamental limitations of relying solely on static features for dynamic runtime failure prediction?
\end{itemize}

\textbf{Dataset Split (Temporal Validation):} 
To simulate a realistic CI/CD pipeline, we employ a temporal split rather than a random split. The build records are sorted by their \texttt{build\_timestamp}. We allocate the oldest 70\% of builds for training, the next 15\% for validation (hyperparameter and threshold tuning), and the most recent 15\% for testing.

\textbf{Evaluation Metrics:} 
Because build failures are rare events (highly imbalanced dataset), standard Accuracy is a misleading metric. Therefore, we evaluate the model using \textbf{Precision}, \textbf{Recall}, and the \textbf{F1-Score}. Precision measures the correctness of our failure alerts, while Recall measures our ability to capture all actual failing builds.

\subsubsection{RQ2 \& RQ3: Root Cause Analysis for Low Recall and Precision}
The underwhelming F1-Score and significantly low Recall (as seen in our Test results) reveal critical insights into the nature of LRTS environments. We speculate three fundamental root causes for this performance degradation:

\textbf{1. The Semantic Gap between Static Structure and Dynamic State:} 
Our model relies purely on static AST call graphs (e.g., Method A calls Method B). However, runtime test failures are rarely caused by the mere existence of a call. They are typically triggered by specific data states, edge-case variable values, or concurrent execution timings. A static GCN cannot observe these runtime states, making it fundamentally "blind" to the actual causes of dynamic regressions.

\textbf{2. Oversmoothing and Coarse Granularity:}
In our architecture, the node states from the entire project graph are mean-pooled into a single 'Project Embedding'. For massive industrial repositories like Hadoop or Kafka, pooling tens of thousands of method nodes into one vector causes severe information loss (oversmoothing). The model fails to isolate the exact localized risk of a small commit, diluting the failure signal.

\textbf{3. Over-reliance on Historical Metadata:}
Because the structural graph embedding is too coarse, we speculate that the MLP classifier heavily overfits to the temporal CI metadata (e.g., \texttt{project\_recent\_fail\_rate}). If a project has been stable recently, the model aggressively predicts 'Pass', leading to a high False Negative rate (thus, plummeting the Recall). This proves that history-based heuristics alone cannot predict 'First Failures' originating from entirely new code modifications.

Specifically, our exhaustive attempts to extract dynamic method-level coverage involved directly instrumenting the legacy build systems. We executed customized terminal commands (e.g., injecting \texttt{jacoco:prepare-agent} directly into the \texttt{mvn test} lifecycle) and strictly manipulated JVM environment variables to prevent infinite deadlocks. Despite these deep engineering efforts, the inherent fragility of the legacy LRTS environment, such as unresolved dependency trees and extreme build timeouts, rendered the comprehensive extraction of dynamic coverage technically unfeasible, forcing our pivot to a static-only approach.

\textbf{Conclusion of the Analysis:} 
Our empirical failure to achieve high performance with a static-only GCN inadvertently proves our initial hypothesis: \textbf{Method-level Dynamic Coverage is strictly necessary for accurate Test Case Prioritization.} The technical bottlenecks we experienced in extracting JaCoCo traces (Section 3.2) must be resolved by future engineering efforts, as static fallbacks are inadequate for the complexities of LRTS.
