\section{Proposed Technique}

\subsection{Approach Overview}
% [proposal] Describe different components and stages of your technique using text/figure/example/flowchart/etc. 
Our proposed technique, GNN TCP, consists of three main stages. First is Graph Construction, where we parse the source code and test suite to build a Code Dependency Graph (CDG) representing the relationships between methods and tests. Second is Change Embedding, where we map the specific code changes from the current commit onto the graph nodes. Third is Failure Prediction, where a Graph Neural Network propagates the impact features of the changed nodes across the graph to predict the failure probability of test nodes.

To predict build failures without relying on computationally expensive dynamic profiling, our pipeline utilizes a purely static representation of the software combined with historical CI metadata. The rigorous formulation of our static graph construction is detailed below.

We represent the source code of a project as a directed static call graph, $G = (V, E)$. The node set $V$ represents the methods parsed from the \texttt{.java} files, and the edge set $E$ represents the static method invocations (i.e., Method A calls Method B). 

To construct this topology across massive open-source repositories, we employ the Python \texttt{javalang} library to parse the Abstract Syntax Tree (AST) of the production code. Specifically, we systematically traverse the AST to identify \texttt{MethodDeclaration} nodes. Within each method, we locate all \texttt{MethodInvocation} entities. By linking the caller methods to the callee methods, we effectively form the static directed edges $E$. This approach allows us to capture the fundamental structural dependencies of the entire project without the overhead and environment conflicts associated with dynamic execution traces.

% About GNN model

We represent the software project as a heterogeneous graph $G = (V, E)$. The node set $V$ includes two types of nodes: Method Nodes, representing source code functions, and Test Nodes, representing test cases. The edge set $E$ captures dependencies including Call Edges, where method A calls method B, and Cover Edges, where test T executes method A. This structure allows us to capture the ripple effect of a bug from a modified method to a potential test failure.

For Code Change Representation, we identify the modified methods for every commit. We assign initial feature vectors to these nodes using a pre-trained code embedding model, such as CodeBERT, to capture the semantic nature of the change. Unchanged nodes are initialized with a zero state or structural embedding vector.

Regarding the GNN Model, we utilize a Relational Graph Convolutional Network (R GCN) to handle the different edge types. The GNN iteratively updates the representation of each node by aggregating information from its neighbors. The core intuition is that a Test Node connected to a Modified Method Node, even indirectly through multiple hops, will accumulate a higher risk score during the message passing phase. The final layer is a Multi Layer Perceptron (MLP) that outputs a scalar $p_i \in [0, 1]$ for each test node $i$, representing the probability of failure.
